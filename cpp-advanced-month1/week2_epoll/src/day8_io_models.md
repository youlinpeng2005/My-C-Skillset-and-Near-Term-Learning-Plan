# Day8：5种IO模型全景（4月26日）

## 必读原理

### 5种IO模型对比

```
模型              | 调用方  | 数据就绪等待 | 数据拷贝（内核->用户）| 特点
-----------------|---------|------------|---------------------|----
阻塞IO(BIO)      | 同步    | 阻塞        | 阻塞                 | 最简单，一线程一连接
非阻塞IO(NIO)    | 同步    | 轮询(busy)  | 阻塞                 | CPU浪费，需配合多路复用
IO多路复用        | 同步    | 阻塞(select)| 阻塞                 | 一线程多fd，主流服务器方案
信号驱动IO        | 同步    | 非阻塞      | 阻塞                 | 用 SIGIO，少见
异步IO(AIO)      | 异步    | 非阻塞      | 非阻塞               | 完全异步，Linux 支持有限
```

### select / poll / epoll 核心区别

| 对比点       | select          | poll            | epoll              |
|------------|-----------------|-----------------|-------------------|
| fd 数量限制  | 1024（FD_SETSIZE）| 无限制           | 无限制              |
| fd 监视方式  | 位图（O(n)遍历）  | 数组（O(n)遍历）  | 红黑树（O(logn)增删）|
| 就绪通知方式  | 线性扫描返回      | 线性扫描返回      | 就绪链表（O(1)获取） |
| 内核态/用户态 | 每次复制 fd 集合  | 每次复制 fd 数组  | 用 mmap 共享内存    |
| 触发模式     | LT              | LT              | LT 和 ET           |
| 时间复杂度    | O(n)            | O(n)            | O(1)（就绪事件获取） |

**结论**：fd 数量少用 select/poll，生产环境用 epoll。

## epoll_wait 内核执行路径（画图理解）

```
应用层调用 epoll_wait(epfd, events, maxevents, timeout)
         |
         v
内核：检查就绪链表（ready_list）
         |
    +----|----+
    | 空      | 非空
    v         v
等待(阻塞)  将就绪 fd 拷贝到 events 数组返回用户态
或超时返回
```

### epoll 内核数据结构

```
epoll 实例（epfd）
├── 红黑树（rbr）：存储所有监视的 fd
│   ├── fd=3（监听socket）
│   ├── fd=5（客户端连接）
│   └── fd=7（客户端连接）
└── 就绪链表（rdllist）：内核回调时插入有事件的 fd
    └── fd=5（有数据可读）← 内核网络栈在数据到达时插入
```

## 自测问题

Q1: 为什么 select 的 fd 上限是 1024？能修改吗？  
A:select 的 1024 限制来源于 fd_set 位图大小，可以通过宏修改，但由于其 O(n) 扫描和拷贝机制，扩展意义不大。
Q2: epoll 为什么比 select 快？核心原因是什么（不是"因为用了红黑树"）？  
epoll 比 select 快的核心原因是避免了对所有 fd 的轮询扫描，通过事件驱动机制只返回就绪 fd，从 O(n) 降为接近 O(1)。
Q3: IO多路复用解决了什么问题？ 
 IO 多路复用解决的是单线程无法同时处理多个阻塞 IO 的问题，使一个线程能够高效管理大量连接。
Q4: 阻塞IO + 多线程 vs 非阻塞IO + IO多路复用，各自的适用场景？  
阻塞 IO + 多线程适合低并发、业务逻辑复杂的场景；非阻塞 IO + IO 多路复用适合高并发 IO 密集型场景，通过事件驱动减少线程数量，提高系统整体吞吐能力。
