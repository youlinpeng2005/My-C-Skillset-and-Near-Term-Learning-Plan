## 三、`messages` 表

```sql
id, sender_id, receiver_id, content, created_at
```

**id 为什么用 BIGINT 而不是 INT**：

<!-- 聊天记录量级估算：1 万用户，每人每天发 100 条，一年多少条？INT 上限是多少？ -->
在聊天系统中消息增长速度非常快，按 1 万用户每天每人 100 条计算，一年约 3.65 亿条消息，而 INT 的上限约 21 亿，长期运行很容易溢出，因此使用 BIGINT 可以提供更大的容量范围，避免系统在中长期运行中出现主键耗尽问题，同时也更适合互联网级数据增长场景。

**content 用 TEXT 而不是 VARCHAR**：

<!-- VARCHAR 最大多少字节？TEXT 的限制是什么？聊天消息该用哪个，为什么？ -->
聊天内容长度具有不确定性，可能包含长文本、表情、JSON 或富文本结构，而 VARCHAR 存在长度上限（理论 65535 字节但实际更小），容易在业务扩展时受限，因此使用 TEXT 类型可以提供更大的存储空间上限（64KB 及以上扩展类型甚至更高），在保证灵活性的同时避免未来字段扩展成本。

**没有加外键约束的理由**：

<!-- 外键的好处是什么？高并发下为什么很多团队禁用外键（性能 + 分库分表）？你的决策是什么？ -->

在高并发 IM 系统中，外键约束会在插入和更新时增加额外的父表校验开销，影响性能，同时在未来分库分表架构下外键无法跨库使用，因此实际工程中通常由应用层保证数据一致性，而不是依赖数据库外键，从而换取更高的性能和更好的扩展性。
**暂时没有"群聊"字段**：

<!-- 现在只支持单聊，将来要支持群聊，这张表需要怎么扩展？ -->
当前 messages 表仅支持 sender_id 和 receiver_id 的单聊模型，结构简单适合快速开发，但未来如果扩展群聊，需要引入 group_id 或 conversation_id 来统一管理消息归属，否则无法支持一对多消息分发，因此当前设计属于单聊阶段的最小可用模型，为后续 IM 架构升级预留扩展空间。

## 四、`friends` 表

```sql
user_id, friend_id, status, created_at
```

**联合主键 (user_id, friend_id) 的含义**：

<!-- 这个设计保证了什么？(1,2) 和 (2,1) 是同一对好友关系还是两条记录，你怎么选，为什么？ -->
联合主键保证一对用户关系在表中唯一存在，避免重复好友记录，同时采用 (user_id, friend_id) 的设计可以清晰表示“从用户视角出发的好友关系”，在实际工程中通常会采用双向存储（A->B 和 B->A），以简化查询逻辑并提升好友列表查询效率。

**status 字段的语义**：

<!-- 0 / 1 / 2 分别代表什么状态（pending / accepted / blocked）？为什么用 TINYINT 而不是 ENUM？ -->
status 字段用于表示好友关系的状态，一般使用 TINYINT 进行编码，例如 0 表示待确认、1 表示已成为好友、2 表示已拉黑，这种设计相比 ENUM 更加灵活，便于后续扩展状态类型，同时也避免了修改枚举结构带来的数据库迁移成本。


**没有加外键约束的理由**：

<!-- 同 messages 表，说明你的决策 -->
与 messages 表一致，friends 表同样不使用外键约束主要是为了提升高并发场景下的写入性能，并避免未来分库分表导致的跨库外键失效问题，因此一致性由应用层逻辑保证，例如在添加好友关系时先校验用户是否存在，从而在性能与一致性之间做工程权衡。
